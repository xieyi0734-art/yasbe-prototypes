# Merkle Science 加密出入金钱包风险扫描 — API 需求梳理与注意点

> 日期：2026-09-10（2026-09-14 更新：管理端口径按 09-14 原型实测对齐；风险阈值确认。**2026-09-18 更新：阈值改为 0–2 自动通过 / 3–5 不自动通过转人工（同日二次修订，Medium(3) 起转人工）；管理端列表 16 列（新增「退款状态」）；入金拒绝后后台自动原路退款；拒绝理由客户端回显（PRD F-014）**）
> 目的：为「出入金扫描对方钱包 → 风险警报 → 人工审核」能力梳理 Merkle Science Compass API 的对接需求与工程注意点。
> 业务硬约束：风险命中（3–5 级）= 不自动入账 / 不自动出金，订单一律转人工复核；入金拒绝 → **后台自动原路退款**，出金拒绝 → 出金失败；**拒绝理由对客户端可见**（脱敏后，见 PRD F-014）。

## 二、风险等级模型（核心枚举）

`risk_level` 为数值 0–5，同时返回 `risk_level_verbose` 文本：

| risk_level | verbose | 含义 | 本业务默认处置 |
|---|---|---|---|
| 0 | No Risk Detected | 无风险 | **自动通过**（不入人工） |
| 1 | Info | 信息级 | **自动通过** |
| 2 | Caution | 谨慎 | **自动通过**（可配置为拦截） |
| 3 | Medium | 中风险 | **不自动通过** · 转人工复核 |
| 4 | High | 高风险 | **不自动通过** · 转人工复核 |
| 5 | Critical | 严重风险 | **不自动通过** · 转人工复核（优先） |

告警等级（`level` / `level_verbose`）同样为 Info / Caution / Medium / High / Critical 五档。

> ✅ **风险阈值已确认（2026-09-18 二次修订）**：`risk_level 0–2`（No Risk Detected / Info / Caution）→ **自动通过**；`risk_level 3–5`（Medium / High / Critical）→ **不自动通过**，转风控人工复核；`Caution（2）` 保留「可配置为拦截」开关（默认不拦），Medium（3）起已默认转人工复核。

## 三、钱包扫描（地址筛查）业务模型（核心）

本业务**只用钱包扫描**（Address Screening / KYA — Know Your Address），弃用交易筛查（KYT — Know Your Transaction）。

### 3.1 什么是钱包扫描

`POST /addresses/` 对**单个钱包地址**做风险评估，返回该地址的 `risk_level`（0–5）及命中告警明细。评估维度：

- **直接风险（Direct Risk）**：地址持有者本身的身份风险（如属于制裁 / 恐怖组织 / 诈骗实体）。
- **关联 / 暴露风险（Association / Exposure Risk）**：该地址与风险对手方的资金往来——直接暴露（1 hop 内直接收发）与间接暴露（1 hop 之外可追踪到的关联）。
- **行为风险（Behaviour Risk）**：交易行为异常（资金量突变、混币模式等）。

### 3.2 为什么只用钱包扫描（弃交易筛查）

1. 交易筛查的 Basic 模式会**双侧**扫尽交易的所有发送方 + 接收方，平台归集 / 热钱包一并入筛，**误报率高**（官方明确）。
2. 交易筛查需处理 UTXO / 多币种 / 未确认交易等链上复杂性，合规运营难判断。
3. 钱包扫描直接筛「对方钱包地址本身」的风险，语义清晰，恰好匹配「出入金都只扫对方钱包」的业务诉求。

### 3.3 `type` 参数语义（关键澄清）

`POST /addresses/` 的 `type` 参数**只用于把地址关联到客户**，**不影响风险评分**：

- `type=1`：地址作为客户的「入金地址」（客户在该地址接收入金）。
- `type=2`：地址作为客户的「出金地址」（客户向该地址发起提现）。

> ⚠️ **入金语义错位待确认**：Merkle 的 `type=1` 语义是「客户自己的入金地址（接收方）」，但本业务入金要扫的是**发送方钱包**（外部打款地址），两者并非同一地址。建议：入金筛查时 `type` 仅作业务侧归类标记（传 `type=1` 表示「入金方向筛查」），或干脆不传 `type`（以 `identifier + blockchain + customer_id` 为主键），后续 `GET /alerts/` 用 `customer_id` 维度归类。详见 §七 决策 6。

## 四、核心端点与业务映射

### 4.1 钱包地址筛查（KYA — Know Your Address）
- `POST /api/v4/addresses/`
- 入参：`identifier`（钱包地址）、`blockchain`（链代码）、`customer_id`（关联平台客户，可选）、`type`（1=入金地址 / 2=出金地址，仅归属、不影响评分）、`show_alerts`（返回 top 10 告警）、`custom_tags`（可选自定义标签）。
- 出参（关键字段）：`risk_level` / `risk_level_verbose`、`total_incoming/outgoing_value`、`balance`、`originator[]`（直接/间接风险来源）、`beneficiary[]`、`digital_assets[]`、`tags`。

### 4.2 交易筛查（KYT）【已弃用】
- `POST /api/v4/transactions/` 本业务**不使用**，改由 4.1 钱包扫描替代。保留仅为背景对照：交易筛查按交易哈希筛整笔交易的双侧地址，需处理 UTXO/多币种/未确认交易，误报率高。

### 4.3 告警查询与处理
- `GET /api/v4/alerts/` — 按 `identifier` / `blockchain` / `customer_id` / `type` / `status` / `level` 过滤告警。
- `POST /api/v4/alerts/resolve/` — 处理告警（运营审核后回写 Merkle，保持合规留痕）。

### 4.4 事件回调（Webhook）
- 风险等级在首次筛查后**可能发生变化**（地址后续被标记）。需订阅 Webhook 实现持续监控；回调用 `X-WEBHOOK-KEY` 校验来源。

### 4.5 其它
- `POST /api/v4/customers/` — 客户级风险筛查（可选，用于聚合客户风险画像）。
- `GET /api/v4/health/` — 健康检查（服务可用性探针）。
- 报告下载 / 币种代码表 / 告警状态表 — 辅助能力。

## 五、出入金业务时序（钱包扫描模型）

### 入金（Deposit）
```
链上交易确认
  → 解析发送方钱包（对方钱包）
  → POST /addresses/（扫发送方钱包）
  → risk_level 分档？
      ├─ 0–2 级 → 自动通过，自动入账（交易状态「已完成」）
      └─ 3–5 级 或 筛查失败 → 交易状态「处理中」（挂账待复核），生成风险告警，通知运营
            → 运营复核（放行需填复核意见、拒绝需填拒绝理由；空值不可提交）
                ├─ 通过 → 入账（交易状态「已完成」）
                └─ 拒绝（理由必填）→ 交易状态「已拒绝」+ **后台自动原路退款**（退款中 → 已退款 / 退款失败）+ **理由回显客户端**（F-014）+ 回写 Merkle resolve（客户端文案「已退款」，见 PRD D7）
```

### 出金（Withdrawal）
```
用户提交提现（含 2FA 校验）
  → POST /addresses/（扫接收方钱包 / 提现目的地址）
  → risk_level 分档？
      ├─ 0–2 级 → 自动通过，提交链上出金（处理中 → 转账中 → 已完成）
      └─ 3–5 级 或 筛查失败 → 交易状态「处理中」（暂缓出金），生成风险告警，通知运营
            → 运营复核
                ├─ 通过 → 放行出金（处理中 → 转账中 → 已完成）
                └─ 拒绝（理由必填）→ 交易状态「已拒绝」+ 资金解冻退回可用余额（客户端文案「出金失败」+ **理由回显**）+ 回写 Merkle resolve（出金拒绝不触发自动退款）
（可选）出金链上确认后 → Webhook 持续监控（地址风险后续变化，非交易筛查）
```

## 六、需求注意点（工程 + 合规）

### A. 安全
1. **API Key 只允许服务端持有**，禁止出现在任何客户端代码、日志、前端请求中。
2. 记录密钥时一律脱敏（`[REDACTED]`），不写入 PRD / 文档 / 提交历史。

### B. 筛查正确性（最关键）
3. **只用钱包扫描**：出入金都只对「对方钱包地址」调 `POST /addresses/`，平台归集/热钱包本就不作为「对方钱包」入筛，无双侧误报问题。
4. `customer_id` 用于把地址关联到平台客户，便于 `GET /alerts/` 按客户归类；`type`（1/2）仅作归属标记、**不影响评分**，入金扫发送方时的 type 语义见 §三 3.3。
5. 地址格式需做**链级校验**（EVM 用 `0x` 前缀、BTC/Solana 等各自格式），格式非法直接拒绝，不送 Merkle。

### C. 性能与可用性
6. 限流 100 次/分钟，需设计**队列 + 背压**，避免批量入金/出金高峰期打满配额。
7. 筛查是**同步调用**，需定义超时（建议 ≤ 3s）；超时/5xx 的兜底策略需明确：
   - **fail-closed**（推荐，合规优先）：超时按「需人工复核」处理（**不进自动通过**、转人工），宁可人工多审不放过。
   - fail-open：超时放行（合规风险高，不推荐默认）。
8. Webhook 持续监控：已筛查地址后续风险等级变化，需触发**重审**（二次拦截 + 通知运营）。

### D. 审核闭环与留痕
9. 运营审核动作（批准/拒绝、理由、时间、操作人）必须**全量留痕**。
10. 审核结果需**回写 Merkle**（`POST /alerts/resolve/`），保持双方合规记录一致。
11. 告警状态需与平台订单状态做**映射与同步**（pending → 审核中 / resolved → 已处置）。

### E. 资金与订单状态机
12. 入金拒绝 = **原路退款**，需定义退款路径（回退到来源钱包 / 挂账待处理）。
13. 出金拒绝 = **出金失败**，资金解冻回用户可用余额，不可自动重试放行。
14. 用户可见状态文案需新增/复用：`pending review`（风控审核中）、`refunded`（已退款）、`failed`（出金失败），且需向用户说明「因合规风控审核」而非「技术故障」。

### F. 数据与合规
15. 平台资产（币种/链）需映射到 Merkle 的 `blockchain` 代码表（`currency` 主要供交易筛查使用，本业务可暂不涉及）。
16. 高风险告警需支持导出合规报告（Merkle 报告下载能力）供审计。
17. 风险阈值、筛查开关、告警等级→处置策略建议做成**管理端可配置**（风控规则）。
