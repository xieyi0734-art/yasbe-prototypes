## 1. 产品概述

### 1.1 背景
YASBee 平台现有加密出入金能力（客户端 Crypto 交易模块 + 管理端「加密货币」节点）。当前出入金在链上确认后直接入账 / 出金，缺乏对**对方钱包**的合规风险筛查。为满足反洗钱（AML）与制裁合规要求，需引入 Merkle Science **钱包地址风险扫描（KYA — Know Your Address）** 能力：出入金均只对「对方钱包地址」调 `POST /addresses/` 做风险评估，**不使用交易筛查（KYT）**，取舍理由见 §1.5。

### 1.2 目标
- 在入账 / 出账动作**之前**，对「对方钱包」执行 Merkle Science 风险扫描。
- 命中 3–5 级风险的订单**不自动入账 / 不自动出金**，交易状态置「处理中」，转风控人工复核（0–2 级自动放行，无需人工）。
- 入金拒绝 → **原路退款**；出金拒绝 → **出金失败**。
- 审核动作全量留痕，并与 Merkle 告警处理结果（resolve）保持同步。

### 1.3 范围
**In-scope**
- 加密入金发送方钱包扫描 + 风险告警 + 人工审核（批准入账 / 拒绝退款）。
- 加密出金接收方钱包扫描 + 风险告警 + 人工审核（批准放行 / 拒绝出金失败）。
- 管理端新增「加密货币管理 → 加密风险扫描」节点：交易风险扫描与审核队列（**单表 + 类型筛选**）+ 审核详情弹窗（MS 风险信息 + 审批闸门）。
- 客户端交易记录新增风险相关状态展示与合规提示（原型现状：`processing` → 文案「该笔交易正在接受合规审核，审核通过后自动完成」；出金结果页 `pending`「审核中」/ `declined`「已拒绝」；2026-09-18 新增详情「拒绝原因 · Rejection Reason」区块回显审核理由（F-014）；`Counterparty Wallet` 列与独立「已退款 / 出金失败」文案未落地，见 D7 / D11）。
- 风险阈值 / 告警等级 → 处置策略的可配置能力（风控规则）。

**Out-of-scope（本期不做）**
- 客户级跨链风险聚合画像（`POST /customers/`）—— 后续增强。
- 已入账 / 已出金交易的持续监控重审（Webhook 二次拦截）—— 后续增强，见 F-011。
- Merkle 合规报告（PDF）在线导出 —— 后续增强。

### 1.4 术语
| 术语 | 定义 |
|---|---|
| 对方钱包 | 入金时的**发送方钱包**；出金时的**接收方（目的）钱包** |
| 钱包扫描（KYA） | 对单个钱包地址调 `POST /addresses/` 做风险评估，返回 `risk_level` 与命中告警；本业务**唯一**使用的筛查方式 |
| 风险告警 | Merkle Science 返回 `risk_level 3–5`（Medium / High / Critical，不自动通过）时产生的待处置记录 |
| 扫描状态 | MS 地址筛查进度：`待扫描` / `扫描中` / `已完成` / `失败`（失败＝接口超时或无响应） |
| 待复核订单 | 3–5 级或筛查未完成、需风控人工处置的交易（管理端以「交易状态 = 处理中」+ 人工复核闸门体现） |
| 原路退款 | 入金被拒后资金**自动**退回来源钱包（后台资金动作，状态：退款中 → 已退款 / 退款失败；客户端呈现「已退款」，见 D7） |
| 出金失败 | 出金被拒后资金解冻退回用户可用余额（客户端呈现「出金失败」，见 D7） |
| 加密风险扫描 | 管理端承载本能力的页面（现网「加密货币管理」组内新增节点，页名/路由见 D12） |

### 1.5 关键取舍：钱包扫描（KYA）替代交易筛查（KYT）
本业务**只做钱包地址筛查**，弃用交易筛查，理由：

- 交易筛查会对交易**双侧**（全部发送方 + 接收方）筛查，平台归集 / 热钱包一并入筛，**误报率高**（官方明确）。
- 交易筛查需处理 UTXO / 多币种 / 未确认交易等链上复杂性，运营难判断。
- 钱包地址筛查直接评估「对方钱包地址本身」的风险（直接风险 / 关联暴露风险 / 行为风险），语义清晰，恰好匹配「出入金都只扫对方钱包」的业务诉求。

`POST /addresses/` 的 `type` 参数**只用于把地址归属到客户**，不影响风险评分：`type=1` = 作为客户的入金地址，`type=2` = 作为客户的出金地址（入金扫的是发送方钱包，其 `type` 取值见 D6）。

## 3. 功能需求

> 功能点编号 F-XXX。每个功能含 优先级 / 用户故事 / 业务规则 / 异常流程 / 字段定义 / UI 说明 / API。

### F-001 入金发送方钱包风险扫描
- **优先级**：P0（Must）
- **用户故事**：作为平台，当一笔加密入金交易在链上确认后，我要在入账前扫描发送方钱包，命中风险则不自动入账。
- **业务规则**：
  - 触发时机：链上交易确认后、入账动作之前。
  - 调用 Merkle `POST /api/v4/addresses/`，对**发送方钱包地址**做风险筛查；`type=1` 仅作「入金方向」归属标记，**不影响评分**（见 §1.5）。
  - `risk_level 0–2`（No Risk Detected / Info / Caution）→ **自动通过**，自动入账（交易状态「已完成」）；`risk_level 3–5`（Medium / High / Critical）→ **不自动通过**，交易状态置「处理中」（挂账待审、闸门禁止审批），生成风险告警并通知运营（阈值口径见 F-009 / D1）。
  - 地址格式非法 → 直接拒绝，不送 Merkle。
- **异常流程**：
  - Merkle 超时 / 5xx → fail-closed：扫描状态置「失败」、审批闸门禁止放行（见 F-012）。
  - 筛查返回但无告警 → 正常入账。
- **字段定义**：见附录 A.1（钱包地址筛查入参 / 出参）。
- **UI 说明**：客户端交易记录对应订单显示合规审核状态；管理端进入「加密风险扫描」列表（类型 = 充值）并置闸门「不允许审批」。
- **API**：`POST /addresses/`（type=1）。

### F-002 出金接收方钱包风险扫描
- **优先级**：P0（Must）
- **用户故事**：作为平台，当用户提交加密出金（含 2FA 校验通过）后，我要在出账前扫描接收方钱包，命中风险则暂缓出金。
- **业务规则**：
  - 触发时机：用户出金提交（2FA 通过）后、链上广播之前。
  - 调用 Merkle `POST /api/v4/addresses/`，对**接收方（目的）钱包地址**做风险筛查；`type=2` 仅作「出金方向」归属标记，不影响评分。
  - `risk_level 0–2` → **自动通过**，提交链上出金；`risk_level 3–5` → **不自动通过**，交易状态置「处理中」（暂缓出金、闸门禁止放行），生成风险告警并通知运营。
- **异常流程**：同 F-001，超时 fail-closed，闸门禁止放行。
- **字段定义**：见附录 A（地址筛查入参/出参）。
- **UI 说明**：客户端交易记录对应订单显示合规审核状态；管理端进入「加密风险扫描」列表（类型 = 提现）并置闸门「不允许审批」。
- **API**：`POST /addresses/`（type=2）。

### F-003 风险告警生成与订单状态机
- **优先级**：P0（Must）
- **用户故事**：作为系统，我要在风险命中时生成告警、驱动订单状态流转，并保证资金不提前入账/出账。
- **业务规则**：见 §7 状态机。
- **字段定义**：告警含 `identifier`（钱包地址）、`risk_level`、`type`、`status`、`level`、`blockchain`、`customer_id`。

### F-004 管理端风险扫描与审核队列
- **优先级**：P0（Must）
- **用户故事**：作为运营，我要在「加密货币管理 → 加密风险扫描」一屏看到全部出入金交易的对手方钱包筛查状态与风险等级，并按类型 / 风险 / 扫描状态筛选后进入复审。
- **业务规则**：
  - **单表**承载入金 + 出金（不拆两条队列），以「类型」列（充值 / 提现）与类型筛选区分方向。
  - 列表 **16 列**（顺序固定）：ID / 客户 ID / 客户名称 / 类型 / 资产 / 链 / 金额 / 手续费 / 对手方钱包地址 / 风险等级 / 筛查结果 / 扫描状态 / 扫描时间 / 交易状态 / **退款状态** / 操作（操作列固定最右）。
  - 筛选：关键词（ID / 客户 / 钱包地址）、类型、风险等级（`0`–`5` 六档 / 未扫描）、扫描状态（待扫描 / 扫描中 / 已完成 / 失败）、交易状态（处理中 / 转账中 / 已完成 / 已拒绝）、筛选时间区间；分页 10 / 20 / 50 条。
  - 统计卡 4 张（数值由列表数据**实时计算**，不硬编码）：待人工复核（3–5 级）、已自动通过（0–2 级）、筛查未完成（待扫描 / 扫描中 / 失败）、退款处理中（入金拒绝后后台自动退款进行中）。
  - 操作列：**交易状态为「处理中」且类型为充值 / 提现**的订单显示「复审」（打开详情弹窗）—— 含两类：**3–5 级待人工复核**（弹窗内可放行 / 拒绝）与**扫描未完成**（待扫描 / 扫描中 / 失败；弹窗内提示先点「重新扫描」，审批按钮禁用）；其余（0–2 级已自动通过、已拒绝、转账中、已完成）显示「查看」（只读详情）。
  - 处置后交易状态更新，列表、统计卡与分页同步刷新，动作写入审核日志。
  - **异常流程**：扫描失败（MS 接口超时 / 无响应）的行，风险等级 / 筛查结果 / 扫描时间显示 `-`、扫描状态「失败」；详情内给出失败原因且**禁止审批**，可用「重新扫描」重试（F-013）。
- **UI 说明**：沿用现网浅色管理端外壳与表格范式（主色 `#E59303`）；页面标题「加密风险扫描」，页副文案「对加密出入金的对手方钱包地址执行 Merkle Science 地址风险筛查（KYA）· 入金筛查来源地址、出金筛查提现地址」。

### F-005 风险审核详情弹窗（MS 风险信息 + 审批闸门）
- **优先级**：P0（Must）
- **用户故事**：作为运营，我要在弹窗内看到 MS 风险等级 / 评分 / 筛查结果 / 命中类别 / 工作流状态 / 扫描时间与完整交易信息，并清楚知道当前能否审批、不能审批的原因是什么。
- **业务规则**：
  - 标题：充值 → 「充值详情」、提现 → 「提现详情」；副标题为交易 ID；顶部展示交易状态标签。
  - **「MS 风险信息」块**（标题右侧标注 `Merkle Science · 钱包地址风险筛查`；块右上为扫描状态标签 + 「重新扫描」按钮）：风险等级（`risk_level` 整数 + `risk_level_verbose`）/ 映射档位（业务四档）/ 风险来源明细（对手方实体名 + 暴露类型 `exposure_type`）/ 累计流入流出金额 / 地址标签 / 扫描时间。**不展示臆造的 `x / 10` 评分** —— Merkle 地址筛查只返回整数 `risk_level`（0–5），无任何评分 / 百分比字段（见 D8）。
  - 扫描失败时块内追加「失败原因」（示例：调用 Merkle Science `POST /addresses/` 无响应（HTTP 504），未取得筛查结果）。
  - **审批闸门**：展示「是否允许审批：是 / 否」；为「否」时给出「无法审批原因」，「通过」按钮置为**禁用**（tooltip 显示原因）。
  - 交易信息块（单列：标签在上、只读值框浅灰）——
    - 提现：钱包类型 / 钱包名称 / 钱包持有人姓名 / 选择币种 / 提现地址（含「地址错误将导致资产不可逆损失」警示）/ 交易 Hash / 网络 / 提现金额（含可用余额）/ 网络费用（含预计到账时间）。
    - 充值：钱包类型 / 钱包名称 / 钱包持有人姓名 / 选择币种 / 来源钱包地址（提示「MS 筛查未完成前不得放行」）/ 目标钱包地址 / 交易 Hash / Safeheron 交易 Key / 网络 / 充值金额 / 网络费用。
  - 汇总块：提现 → 提现金额 / 费用 / 总扣除金额；充值 → 充值金额 / 网络费用 / 实际到账。
  - 底部按钮：通过（`#22c55e`）/ 拒绝（`#ef4444`）/ 关闭；点「拒绝」展开必填「拒绝原因」文本域，**空值不可提交**（前端拦截 + 服务端二次校验）；提交后「确认拒绝」。**已拒绝订单再次打开弹窗时不展示可编辑的拒绝原因框，改为只读展示已填理由**（防重复提交与理由被覆盖）。
  - 弹窗规格（现网实测）：宽 672px、圆角 10px、标题 18px/600 + 分隔线、字段值框 `#f5f5f5` 高 40px。
- **风险来源展示**：不臆造「制裁名单 / 黑名单 / 灰名单」等分类；按 Merkle 返回的 `originator[]` / `beneficiary[]` 展示**对手方实体名称（`tag_name_verbose`）+ 暴露类型（`exposure_type`：direct / indirect）**；无暴露时显示「无对手方暴露」。
- **UI 说明**：逐条告警明细（匹配详情 / 置信度 / 直接-间接来源）本期不在弹窗展示，见 D10。

### F-006 入金审核处置（通过入账 / 拒绝退款）
- **优先级**：P0（Must）
- **用户故事**：作为运营，我要通过入账或拒绝并退款，且拒绝必须填写理由。
- **业务规则**：
  - 前置条件：审批闸门「是否允许审批 = 是」—— 精确条件为**扫描状态 = 已完成 ∧ `risk_level` ≥ 3（超出自动通过区间 0–2）∧ 交易状态 = 处理中**；任一不满足则闸门为「否」，「通过」按钮禁用并给出原因（扫描未完成 → 提示先「重新扫描」；0–2 级 → 系统已自动放行）。
  - 通过 → 交易状态置「已完成」，解除挂账、资金计入可用余额；写审核日志（操作人 / 时间 / 动作）。
  - 拒绝 → **必填拒绝理由**（`reject_reason`，字段定义见 F-014）；交易状态置「已拒绝」；**后台自动发起原路退款**（无需人工触发），退款状态独立字段流转「退款中 → 已退款 / 退款失败」；客户端交易详情回显该理由（F-014）；理由 + 操作人 + 时间记入审核日志。
  - 原型现状：管理端弹窗呈现「拒绝 → 必填原因 → 已拒绝 + 退款状态流转 + 拒绝原因只读展示（标注已同步客户端）」；客户端详情回显拒绝理由（F-014）；Merkle `resolve` 回写属后台动作（F-008 / D7）。
  - **异常流程**：退款路径失败 → 退款状态置「退款失败」，挂账异常并生成风控事件转人工跟进。

### F-007 出金审核处置（通过放行 / 拒绝出金失败）
- **优先级**：P0（Must）
- **用户故事**：作为运营，我要通过放行出金或拒绝使出金失败，且拒绝必须填写理由。
- **业务规则**：
  - 前置条件：审批闸门「是否允许审批 = 是」。
  - 通过 → 提交链上出金（交易状态：处理中 → 转账中 → 已完成）；写审核日志。
  - 拒绝 → **必填拒绝理由**（`reject_reason`，见 F-014）；交易状态置「已拒绝」，资金解冻退回用户可用余额（客户端呈现「出金失败」，见 D7）；客户端详情回显该理由（F-014）。**出金拒绝不触发自动退款链路**（资金本就未出账），列表「退款状态」列固定显示 `-`。
  - 出金拒绝后**不可自动重试放行**，用户需重新发起。

### F-008 审核留痕与 Merkle resolve 回写
- **优先级**：P0（Must）
- **用户故事**：作为合规，我要全量追溯每一单的审核记录，并与 Merkle 结果一致。
- **业务规则**：
  - 记录 审核人 / 审核时间 / 动作（通过 / 拒绝）/ 理由 / Merkle 告警 ID / 回写结果。
  - 通过 / 拒绝均调用 `POST /alerts/resolve/` 回写 Merkle；回写失败重试（指数退避），最终失败进「待补回写」队列。
  - 原型现状：回写为后台动作，界面仅提示「写入审核日志」，无回写状态展示（开发落地时补后台状态，不进本期界面）。

### F-009 风险阈值与告警等级配置
- **优先级**：P1（Should）
- **用户故事**：作为合规，我要配置「哪些风险等级拦截进待审」。
- **业务规则**：
  - **阈值已确认（2026-09-18 二次修订）**：`risk_level 0–2`（No Risk Detected / Info / Caution）→ **自动通过**；`risk_level 3–5`（Medium / High / Critical）→ **不自动通过**，转风控人工复核。
  - `Caution（2）` 保留「可配置为拦截」的开关，默认不拦（`Medium（3）` 起已默认转人工复核，如需进一步收紧可上调阈值）。
  - 3–5 级订单进入「待人工复核」，**系统不自动通过**；放行需填写复核意见、拒绝需填写拒绝理由（F-014），两者均写入审核日志。
- **UI 说明**：落现网「风控管理 → 规则管理」，新增 Merkle 风险阈值配置。

### F-010 客户端状态展示与合规提示
- **优先级**：P0（Must）
- **用户故事**：作为客户，我要在交易记录看到订单「正在接受合规审核」，未通过时得到合规解释，而不是技术故障提示。
- **业务规则**：
  - 复用现网状态枚举承载：交易状态 `processing` → 文案「该笔交易正在接受合规审核，审核通过后自动完成」；出金结果页新增 `pending`「审核中」与 `declined`「已拒绝」合规文案（09-11 客户端原型已落地）。
  - **不向客户端暴露 MS 原始风险字段**（`risk_level` / `risk_level_verbose` / 命中实体 / 暴露类型等明细，防恶意方试探）。**唯一例外是拒绝理由**（`reject_reason`）—— 由风控审核人员撰写、经脱敏的话术，用于向客户说明驳回依据，回显规则与脱敏红线见 F-014。
  - 是否新增独立「已退款 / 出金失败」终态文案与徽章 → 见 D7。
- **UI 说明**：原型见 `prototypes/加密出入金风险扫描/2026-09-11_加密出入金风险扫描_客户端.html`（深色主题 `#FFCA00`）；详情弹窗已落地「拒绝原因 · Rejection Reason」区块；`Counterparty Wallet` 列未落地（D11）。

### F-011 持续监控重审（Webhook，后续增强）
- **优先级**：P2（Could，本期不做）
- **业务规则**：订阅 Merkle Webhook，**已筛查的钱包地址**后续风险升级时二次拦截 + 冻结 + 重审（地址维度持续监控，非交易筛查）；校验 `X-WEBHOOK-KEY`。

### F-012 超时兜底与降级（fail-closed）
- **优先级**：P0（Must）
- **用户故事**：作为系统，我要在 Merkle 超时 / 不可用时安全降级，不放过风险单。
- **业务规则**：
  - 筛查超时（建议 ≤ 3s）或 5xx → 扫描状态置「失败」，风险等级 / 筛查结果 / 扫描时间为空（列表显示 `-`），**审批闸门禁止放行**（fail-closed）。
  - 详情弹窗给出失败原因，并提供「重新扫描」重试（F-013）。
  - 配额告警（接近限流）→ 熔断进队列，避免打满 100/min。
  - 恢复后自动补扫，补扫结果若为无风险可自动放行（保留原未完成痕迹）。

### F-013 手动重新扫描（MS 地址筛查重试）
- **优先级**：P1（Should）
- **用户故事**：作为运营，扫描失败或对结果存疑时，我要能对同一钱包地址重新发起筛查。
- **业务规则**：
  - 详情弹窗「MS 风险信息」块提供「重新扫描」，对当前交易的对手方钱包地址重新调用 `POST /addresses/`。
  - 扫描状态置「扫描中」（列表同步显示），接口返回后回填 风险等级 / 筛查结果 / 扫描时间，并刷新闸门状态。
  - 原型现状：已实现（扫描中 → 已完成，含失败重试路径）。
- **API**：`POST /addresses/`（type=1 入金 / type=2 出金）。

### F-014 客户端拒绝理由回显
- **优先级**：P0（Must）
- **用户故事**：作为客户，当我的充值 / 提现被驳回时，我要在交易详情看到具体的驳回原因，而不是只有「已拒绝」三个字 —— 这样我才能判断是收款地址有问题、还是需要补充资金来源证明。
- **业务规则**：
  - **数据来源**：管理端审核动作填写的 `reject_reason`（F-006 / F-007），随审核结果落库并经交易详情接口下发给客户端；**客户端展示即审核人员原文**，不做二次改写或机翻。
  - **展示位置**：客户端「交易记录 → 该笔交易详情」内，位于状态说明文案（如「该笔交易未通过风险审核，资金已保留在账户」）**下方**，独立区块，标题「拒绝原因 · Rejection Reason」。
  - **展示条件**：仅当交易状态 = 已拒绝（`rejected`）且 `reject_reason` 非空时展示。
  - **空值兜底**：历史订单 / 系统自动驳回 / 理由为空 → 展示兜底文案（见 D15），**不展示空白区块、不报错**。
  - **长度与可读性**：单条建议 ≤ 200 字；超长前端截断为 3 行 + 「展开」。支持换行（`pre-wrap`），**不支持 Markdown / HTML**（防注入）。
  - **一致性**：该理由与客户端其它触达渠道（站内通知、客服工单）**同源同文**，不出现管理端写 A、客户端显示 B。
- **脱敏与合规约束（红线）**：
  - 拒绝理由**不得**直接写入：Merkle `risk_level` 数值 / `risk_level_verbose`、命中实体名称（如 Garantex）、名单类型（OFAC SDN / 混币器）等 MS 原始字段 —— 这些属 F-010 禁止对客户端暴露的明细。
  - 管理端拒绝原因输入框需给出**填写指引与示例话术**（如「因交易对手方地址存在合规风险，本次提取未能完成」），提交时做**敏感词提示**（命中 MS 字段名 / 名单名 → 提示运营改写；非硬拦截，可留痕豁免）。
  - 若业务确需向客户或监管披露具体命中事实，走独立的合规披露流程，不在本需求范围。
- **异常流程**：
  - 状态为已拒绝但理由为空 → 展示兜底文案（D15），不报错。
  - 理由含超长无空格串（如钱包地址）→ 强制断行，不横向溢出。
- **字段定义**：

| 字段 | 类型 | 说明 | 来源 |
|---|---|---|---|
| reject_reason | string | 拒绝理由原文（管理端审核填写，≤200 字） | 管理端审核动作 |
| reject_reason_at | datetime | 理由填写时间 | 审核动作时间 |
| reject_reason_by | string | 填写人（风控 / 运营账号） | 审核动作人 |
| reject_reason_visible | bool | 是否对客户端可见（默认 `true`，合规可按需关闭，见 D13） | 平台配置 |

- **UI 说明**：客户端详情区块为红色调提示块（深色主题 `#111418` 底 + 红色系边框与文案），与「已拒绝」状态徽章同色系，底部一行灰字说明「该原因由风控审核人员填写，仅用于说明本次驳回依据」；管理端同一理由在弹窗内以**只读红框**展示并标注「已同步至客户端详情」。原型见 `prototypes/加密出入金风险扫描/2026-09-11_加密出入金风险扫描_客户端.html`（详情弹窗「拒绝原因 · Rejection Reason」区块）。
- **API**：随交易详情接口返回 `reject_reason` / `reject_reason_at`（无独立端点）。

## 7. 状态机

订单状态分两个维度：**扫描状态**（MS 地址筛查进度）与**交易状态**（平台交易流转，枚举对齐现网）。

### 7.1 扫描状态（MS 地址筛查）
```
待扫描 →（提交 POST /addresses/）→ 扫描中 → 已完成（取得 risk_level 与筛查结果）
                                    ↘ 失败（超时 / 5xx / 无响应）→「重新扫描」回到 扫描中
```

### 7.2 入金订单（交易状态）
```
链上确认 → [扫描] → 0–2 级 → 自动通过 → 已完成（入账）
                  → 3–5 级 或 扫描失败 → 处理中（挂账、资金不计入可用余额）
                        → 通过 → 已完成
                        → 拒绝（理由必填）→ 已拒绝 + 后台自动原路退款（退款中 → 已退款 / 退款失败）+ 理由回显客户端（F-014）
```

### 7.3 出金订单（交易状态）
```
用户提交(2FA) → [扫描] → 0–2 级 → 自动通过 → 处理中 → 转账中 → 已完成
                       → 3–5 级 或 扫描失败 → 处理中（暂缓出金）
                             → 通过 → 转账中 → 已完成
                             → 拒绝（理由必填）→ 已拒绝 + 资金解冻退回可用余额（客户端「出金失败」+ 理由回显；不触发自动退款）
```

### 7.4 与 Merkle 告警状态的映射
| 平台侧 | Merkle 状态 | 说明 |
|---|---|---|
| 待扫描 / 扫描中 / 失败 | — | 未取得告警结果，闸门禁止审批（fail-closed） |
| 命中（risk_level ≥ 3） | open | 待人工复核 |
| 通过 / 拒绝后 | resolved | 回写 `POST /alerts/resolve/`（后台动作，见 F-008） |

> 原稿的 `PENDING / COMPLETED / REFUNDED / FAILED` 独立状态集合，现按现网交易状态枚举（处理中 / 转账中 / 已完成 / 已拒绝）+ 客户端文案承载；是否新增「已退款 / 出金失败」终态见 D7。

## 8. 验收标准

- 管理端新增「加密货币管理 → 加密风险扫描」入口，页面为**单表**（非两条队列），含「类型」列与类型筛选（充值 / 提现）。
- 列表 **16 列**及顺序与原型一致（ID / 客户 ID / 客户名称 / 类型 / 资产 / 链 / 金额 / 手续费 / 对手方钱包地址 / 风险等级 / 筛查结果 / 扫描状态 / 扫描时间 / 交易状态 / 退款状态 / 操作），操作列固定最右。
- 4 张统计卡（待人工复核 3–5 级 / 已自动通过 0–2 级 / 筛查未完成 / 退款处理中）数值由列表数据实时计算。
- 筛选支持 关键词 / 类型 / 风险等级 / 扫描状态 / 交易状态 / 时间区间；分页 10 · 20 · 50。
- 详情弹窗含「MS 风险信息」块（风险等级 + `risk_level_verbose` / 映射档位 / 风险来源明细 / 累计流入流出 / 地址标签 / 扫描时间）+ 交易信息块 + 汇总块 + 拒绝原因（必填）+ 自动退款块 + 审批闸门；**不得出现臆造的 `x / 10` 评分**。
- **阈值 `risk_level 0–2` 自动通过 / `3–5` 不自动通过转人工**：3–5 级订单进入人工复核（放行需复核意见、拒绝需理由）；0–2 级系统自动放行。
- 扫描未完成 / 扫描失败的订单同样禁止审批（fail-closed），并提供「重新扫描」重试。
- 拒绝必须填写理由（前端拦截空值 + 服务端二次校验）；已拒绝订单不可再次提交拒绝（理由框转只读展示）。拒绝后交易状态置「已拒绝」，理由 + 操作人 + 时间写入审核日志。
- 入金拒绝 → 后台自动原路退回来源钱包（退款状态：退款中 → 已退款 / 退款失败）；出金拒绝 → 资金解冻退回可用余额，且不可自动重试放行。
- Merkle 超时 / 5xx 时不放过风险单（闸门禁止审批），且不阻断人工流程。
- 出入金全流程**只对「对方钱包地址」调用 `POST /addresses/`**（入金 type=1、出金 type=2），无 `POST /transactions/` 调用（交易筛查已弃用）。
- 客户端**不暴露** MS 原始风险字段（`risk_level` / `risk_level_verbose` / 命中实体 / 暴露类型），仅以合规文案与状态呈现。
- 客户端交易详情**回显拒绝理由**（`reject_reason`），与审核人员填写原文一致，且**不含** MS 原始字段名 / 风险等级数值 / 命中实体名称（脱敏红线，见 F-014）。
- 历史订单 / 系统自动驳回且 `reject_reason` 为空时，客户端展示兜底文案（不展示空白区块、不报错）。

本业务**不使用**。交易筛查按交易哈希对整笔交易的双侧地址筛查（平台归集 / 热钱包一并入筛，误报率高），且需处理 UTXO / 多币种 / 未确认交易；语义与「出入金只扫对方钱包」不符，已由 A.1 钱包地址筛查替代。此处仅作背景对照，`currency` 等入参本业务不涉及。
