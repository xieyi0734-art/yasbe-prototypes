# 站内通知（In-App Notification）功能 PRD

| 项目 | 内容 |
|---|---|
| 产品 | YASBe 客户端（customer.beeznis.com） |
| 功能 | 站内通知中心（含邮件渠道编排） |
| 版本 | v0.1（草案） |
| 日期 | 2026-08-14 |
| 状态 | 待评审 |
| 前置依赖 | 邮件双发治理（见第 7 节） |

---

## 1. 背景与问题

**现状**：系统**没有任何站内通知能力**，事件通知全部走邮件。现有邮件分布在两个系统：

- YasbeeAdmin：18 个场景（KYC/KYB 审核、卡相关、法币/加密资金、账户冻结、运维告警等）
- YasbeeBackend：18 个场景（验证码、提交确认、资金状态、安全提醒、通用通知等）

**邮件现状的硬伤**：对照两边清单，**有 4 个场景在 Admin 和 Backend 同时下发**，用户现在就可能收到同一件事的多封重复邮件（详见第 7 节）。

**用户侧痛点**：
1. 登录后没有任何"事件聚合视图"，资金/审核状态变了只能靠各页面手动刷新。
2. 提现卡单、KYC 驳回等**不主动告知**，用户反复刷新、来回问客服。
3. 安全事件（新设备登录、改密）无提醒，影响信任感。
4. 无"一条业务一条通知"的约定，多状态事件易被拆成多条重复提醒。

---

## 2. 目标与非目标

**目标**：
- 让用户"有事主动知道"：资金与安全事件即时触达，重要事件即使离线也有邮件兜底。
- 提升活跃与信任，降低"我的钱到哪了 / 审核进度"类客服咨询。
- 借本次建设，建立**唯一的事件清单与渠道口径**，顺带治理现有邮件双发。

**非目标（一期不做）**：
- 营销/活动推送（若未来做，默认关闭、需用户主动开启）
- App 推送（APNs/FCM）
- 短信通道
- 站内 IM / 客服会话

**成功指标（建议）**：
| 指标 | 目标 |
|---|---|
| 通知中心月度使用率（看过通知的用户 / 月活） | ≥ 40% |
| 安全类通知送达率 | 100% |
| 资金类通知点击跳转率 | ≥ 30% |
| KYC/KYB 驳回后重新提交率 | 较上线前提升 |
| "提现进度/资金到账"类客服咨询量 | 下降 |

---

## 3. 用户与场景

**角色**：个人用户（KYC）、企业用户（KYB）。内部运维/风控告警不纳入本期站内通知。

**核心用户故事**：
1. 作为用户，入金/充值/提现状态变化时，我希望收到通知并能**一键进详情**。
2. 作为用户，KYC/KYB 被驳回时，我希望**看到驳回原因**并一键回认证页修改。
3. 作为用户，新设备登录/改密时，我希望**立即被提醒**（即使不在线也有邮件）。
4. 作为用户，我想在通知中心**按类型筛选、标记已读**。
5. 作为用户，我不希望**同一件事被反复提醒**。

## 4. 功能需求

### 4.1 通知中心
- **入口**：顶栏🔔铃铛 + 未读数字徽标（超过 99 显示 99+）。
- **列表**：按时间分组（今天 / 昨天 / 更早）；每条含类型图标、标题、摘要、时间。
- **业务类型标注**：每条通知标注所属业务类型（彩色标签：认证 / 法币资金 / 加密资金 / 卡片 / 安全 / 兑换），并标注点击去向（→ 目标模块，与 §5 各表"点去哪"一致）。
- **筛选**：全部 / 未读 / 资金（含法币+加密）/ 卡片 / 安全 / 认证 / 兑换。
- **已读与跳转**：点单条 → 跳转到对应模块页面并标记已读；提供"全部已读"；未读条目有蓝点标识。
- **空态**：插图 + "暂无通知"引导文案（不能只显示 No data）。
- **分页**：默认展示最近一屏，可加载更多。

### 4.2 实时提醒（Toast）
- 高优先级事件（资金到账、安全提醒、审核驳回）在页面内**右上角弹出浮层**，3–5 秒自动消失，可点击进详情。
- 与现有"操作成功/失败"提示（顶部条）**在视觉和位置上有区分**。

### 4.3 未读徽标
- 全局实时刷新未读数；用户已读后递减；清零后徽标消失。

### 4.4 通知偏好设置
- 位置：账户设置 → 通知设置。
- 按类别提供"站内 / 邮件"开关。
- **安全类、资金类强制开启，不可关闭**（合规与信任底线）。

## 5. 事件清单与渠道口径（核心 · 唯一口径）

> 每个事件定义一次"站内/邮件各发不发、谁负责发、用户看到什么、点去哪"。渠道标记：
> **双渠道** = 站内+邮件都发（重要事件）；**只站内** = 进通知中心，默认不另发邮件；**不进** = 保持邮件/原样。

### 5.1 认证类

| 事件 | 现有邮件 | 站内 | 渠道 | 通知文案示例 | 点去哪 |
|---|---|---|---|---|---|
| KYC 提交成功 | Backend #4 | 是 | 只站内 | 您的 KYC 已提交，审核中（预计 X 工作日） | 认证页 |
| KYC 审核通过 | Admin #1 | 是 | 双渠道 | 您的 KYC 已通过，可以开卡了 | 认证页 |
| KYC 审核拒绝（含原因） | Admin #3 | 是 | 双渠道 | 您的 KYC 未通过：{原因}，请修改后重新提交 | 认证页 |
| KYB 提交成功 | Backend #3 | 是 | 只站内 | 您的 KYB 已提交，审核中 | 认证页 |
| KYB 审核通过 | Admin #2 | 是 | 双渠道 | 您的企业认证已通过 | 认证页 |

## 6. 业务规则

### 6.1 一条业务一条通知（防重复核心）
- **状态流事件**（提现、KYC/KYB 审核、加密提现、实体卡物流）从产生到结束只存在**一条通知**，状态随时间线更新（如"处理中 → 已完成"），**不新增多条**。
- **一次性事件**（到账、开卡、驳回）产生一条通知。

### 6.2 渠道编排
- 重要事件（资金、安全、审核结果）：**站内 + 邮件双渠道**，互补不重复。
- 轻量结果（提交成功、首次登录）：默认**只站内**，邮件按用户偏好。
- 验证码与内部告警：**不进通知中心**。

### 6.3 去重
- 同一事件（含系统重试/并发）只产生一条；同类邮件短时间合并为一封摘要。

### 6.4 深链映射
- 每个事件必须有明确去向（见第 5 节各表"点去哪"）。

### 6.5 文案规范
- 标题 + 摘要 + 变量（如 {amount}、{coin}、{last4}、{原因}）；支持中/英双语。
- 金额、币种、卡号尾号等敏感信息**摘要展示、不完整展示**。

## 7. 前置事项：邮件双发治理（建议同版本上线）

现状 4 个场景在 Admin/Backend 重复下发，**必须先定"谁负责发"**，否则叠加站内后三通道重复：

| 场景 | 涉及系统 | 建议 |
|---|---|---|
| 虚拟卡开卡成功 | Admin #7 / Backend #9 | 统一由一方下发，另一处改为事件源上报 |
| 法币充值完成 | Admin #10 / Backend #11 | 同上 |
| 加密充值完成 | Admin #12 / Backend #13/#15 | 统一为一条，其余两处去重 |
| 加密充值待审核 | Admin #11 / Backend #14 | 同上 |

## 8. 非功能需求（产品层面）

- **多语言**：通知文案中/英双语。
- **性能**：通知列表与徽标加载流畅，不影响主流程。
- **移动端**：通知中心在移动端全屏展示，适配小屏。
- **无障碍基础**：图标按钮可读、状态不单靠颜色传达。

---

## 9. 验收标准（产品可测）

1. 顶栏铃铛正确显示未读数；读后递减、清 0 消失。
2. 用户收到"法币入金到账"通知，点击直达法币账户，且该条自动标记已读。
3. 一笔提现从"处理中"到"已完成"，用户只看到**一条通知**，状态在通知内更新。
4. KYC 被驳回时，用户同时收到站内 + 邮件，文案**包含驳回原因**，点击回认证页。
5. 新设备登录提醒为**强制双渠道**，用户在偏好设置中无法关闭。
6. 同一事件因系统重试发生两次，用户**只收到一条**。
7. 验证码类邮件**不进入**通知中心。
8. 通知中心支持按"全部/未读/资金/卡片/安全/认证/兑换"筛选，且每条通知正确标注业务类型标签与跳转目标。
9. 邮件双发场景（开卡、充值完成）治理后，用户**只收到一封**邮件。
10. 中/英文切换后，通知文案随之切换。

## 11. 开放问题（需拍板）

1. **CYRO 产品线**是否纳入本通知中心（收件人/文案体系不同）。
2. 邮件**可配置 CC**（Admin #9/#13）在站内如何体现——建议站内仅面向主收件人。
3. 验证码类未来是否支持站内/App 通道（本期不做，仅记录）。
4. **提现卡单治理**（当前多笔提现长期卡"处理中"）建议与通知**同版本排期**——状态机不修，资金类通知发不准确。
