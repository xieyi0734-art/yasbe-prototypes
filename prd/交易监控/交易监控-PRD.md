# 交易监控 PRD

版本：v0.1  
日期：2026-11-19  
端别：管理端 · 风控管理  
状态：需求评审稿。业务范围沿用既有确认；案件协作流程为本次建议方案，CA 接口契约和生产参数尚待确认。

## 1. 目标与依据

对纳入范围的成功交易实施事后交易监控，提供交易上送核对、告警案件调查和处理留痕。运营可以回答：哪位客户、哪类业务、何时、因什么规则触发、涉及哪些交易、由谁处理以及处理结果是否同步。

依据：

- 用户此前确认的范围：Crypto Wallet 成功链上入金／出金；VA 仅 OpenPayd EUR／GBP 成功入金／出金；Card 充值与 Card 转出到 Crypto Wallet，关注充值后快速转出。
- [在线 Scoping Sheet](https://docs.google.com/spreadsheets/d/1v-cyQqa2HzML41J86wssPyUMF9cIAkopHmKNVMBJITA/edit?gid=1002527305#gid=1002527305)。本次核对已下载文件 `Apex Markets Inc _ Mesh TM Scoping Sheet.xlsx`，主要依据 `4. Scenarios` 第 7–25 行。下载快照不等于生产配置或已签署接口契约。
- [原型目录](../../prototypes/交易监控/index.html)。样例数据全部虚构，不连接 CA，不执行任何真实资金操作。

## 2. 业务边界

| 业务 | 本期纳入事件 | 监控目的 | 排除或约束 |
| --- | --- | --- | --- |
| Crypto Wallet | 成功链上入金、成功链上出金 | 金额、笔数异常 | 非链上内部划转不得伪装成链上交易；失败／处理中交易不计入成功交易监控 |
| VA | OpenPayd EUR／GBP 成功入金、成功出金 | 金额、笔数异常 | 不将 USD／Bridge 纳入本期 |
| YASBe Card | 充值、Card 转出到 Crypto Wallet | 识别充值后快速转出 | 不含开卡、消费、拒付、ATM；消费由 Interlace 既有监控覆盖。充值来源、成功节点、规则阈值待确认 |

本期不开发规则编辑器，不因规则表出现其他规则而扩充业务范围。地址筛查与本模块分开：不沿用地址风险等级来推定 CA 案件优先级。当前交易已成功，页面不提供放行、拒绝、冻结或退款操作；案件结论也不得触发这些资金动作。

Card 转 Wallet 为同一内部转移事件。可保留卡侧与钱包侧记账关联，但不能将钱包到账再次统计为链上入金。客户 UID 是平台归属标识；`customer_identifier.id` 与平台 UID 的映射、租户隔离和多账户归属须在接入时确认。

## 3. 新版规则对产品的影响

| 表内规则 | 来源 | 本次需求表达 |
| --- | --- | --- |
| RL_0013 / RL_0014 单笔出／入金额 | 第 8–9 行 | 保留方向、原币金额、折算金额与币种、阈值。表内为 `> 100,000`，不能擅自解释成 USD 或 USDT |
| RL_0015 入金笔数 | 第 10–12 行 | 分别按 BANK_PAYMENT、CARD_PAYMENT、CRYPTO 过滤，按 `{customer_identifier.id, type}` 统计入金。表内 7 calendar_days、`> 3` |
| RL_0016 出金笔数 | 第 13–15 行 | 同上，方向 OUTBOUND；入／出不可混计 |
| RL_0017 入金累计金额 | 第 16–18 行 | 按客户＋type 统计 `base_value.amount`；表内 7 calendar_days、`> 100,000` |
| RL_0018 出金累计金额 | 第 19–21 行 | 同上，方向 OUTBOUND |
| 余额比例、余额上限、首次交易等其他规则 | 第 7、22–25 行等 | 仅作为供应商规则资料，不自动新增本期需求 |

产品上需要同时展示业务类型、统计对象、规则方向、统计窗口、阈值和实际值。不能仅按客户合并 Bank／Card／Crypto，也不能只凭 RL 编号合并不同类型的规则实例；需保留上游实例标识或其明确的区分字段，具体契约待确认。

注意：

1. `7 calendar_days` 不直接改写为滚动 168 小时，窗口起止、时区及当前交易是否计入以确认后的 CA 契约为准。
2. 金额累计使用供应商认可的折算口径。原币、原始金额、折算币种、折算金额、汇率及汇率时间分开保留；缺失时展示“暂未获取”，不得把 USD 与 USDT 或 EUR 与 GBP 直接相加。
3. 表内 Outcome 为 Allow、Priority 为 P7 - Low。Allow 不等于平台需设置“放行”动作；P7 不映射为地址筛查的 0–5 等级。
4. 表内给出 Card 类型的金额／笔数配置，并不代表用户已追加 Card 全量金额／笔数监控需求。当前 Card 目标仍为充值后快速转出；需与 CA 确认能否用现有规则实现、是否需要组合规则。
5. RL_0020 的逻辑写 730 calendar_days，但问题描述仍提 30 天，存在资料内冲突；该规则不在本期启用范围，不自行选取其一。

## 4. 主流程

1. 平台接收到本期范围内的成功交易事件，持久化交易归属、业务类型、事件类型、金额和原业务标识。
2. 生成监控上送任务，保留业务成功状态与上送状态，两者独立。
3. CA 接收并评估交易。受理成功不表示无风险，也不保证已形成案件；告警／案件回传方式、延迟和取回机制待接口契约确认。
4. 按上游稳定标识接收或更新案件，关联客户、命中规则与交易；重复回传不重复建案。多规则聚合、多笔交易关联方式不可只按客户自行合并。
5. 运营领取案件、查看命中原因及交易、记录调查过程，提交结论。
6. 本地保存结论后发起独立同步任务。失败可重试，重试不重复新增调查记录；若 CA 不支持回写，需在联调前裁定替代流程，不能宣称已同步。

## 5. 页面与交互

### 5.1 案件列表

[打开案件列表](../../prototypes/交易监控/2026-11-19_案件列表_管理端.html)

- 统计条：全部案件、待处理、调查中、已结案。统计范围为当前用户有权限访问的数据，不随列表筛选改变；不能向无权限用户泄露跨租户统计。
- 默认筛选待处理；可按 Case ID／客户 UID、业务、案件状态、负责人、命中规则和创建日期查找。页面支持查询、重置、查看全部案件及分页。
- 列表：Case ID、客户 UID、业务、命中规则、关联交易数、状态、负责人、创建时间、操作。
- 未领取的待处理案件显示领取；确认后负责人变为当前管理员，进入调查中。同一时刻只能一人领取成功，后端需原子校验；原型本地模拟不代表并发能力。
- 点击案件进入独立详情。无数据展示筛选空状态；正式系统的加载失败提供重试，不展示为零条数据。

### 5.2 案件详情

[打开案件详情](../../prototypes/交易监控/2026-11-19_案件详情_管理端.html?id=CASE-DEMO-001)

内容包含：

- 案件概况：Case ID、客户 UID、负责人、创建时间、上游优先级、处理结论、CA 结论同步状态。
- 命中原因：规则标识与名称、业务类型、统计对象、方向、窗口、阈值、实际值与规则依据。生产展示以真实返回为准，不能把表格默认值填成实际命中值。
- 关联交易：时间、业务／事件、原始金额与币种、业务状态、平台交易号。可打开交易详情，或跳转该客户的监控交易记录。
- Card 时间线：按时间展示充值与转出；保留两侧币种与金额。关联依据未确认时仅展示样例，不标注为已验证资金配对、不计算无依据的比例。
- 调查处理：负责人可编辑调查说明并保存草稿；提交须有说明和结论，并二次确认。非负责人只读，已结案和已升级案件不继续编辑原结论。
- 调查记录与日志：区分草稿、已提交结论与操作日志。已提交记录保留，不因同步重试而新增同一结论。

建议的本地状态机：

| 当前状态 | 操作 | 下一状态 | 前提 |
| --- | --- | --- | --- |
| 待处理 | 领取 | 调查中 | 有处理权限，尚无负责人 |
| 调查中 | 保存草稿 | 调查中 | 当前负责人 |
| 调查中 | 未发现异常并提交 | 已结案 | 说明与结论齐全 |
| 调查中 | 发现可疑，升级合规 | 待合规处理 | 说明与结论齐全，保留提交人 |

以上是本次提出的工作流，不等于 CA 原生状态。合规接收队列、复核、退回、重开和最终结案权限尚待确认；首版不伪造这些操作。原型“合规专员”为演示负责人，不是已确定的实际账号。

结论同步状态独立为：无需同步 → 待同步 → 同步成功／同步失败。失败显示原因，授权用户可重试；待同步禁止重复提交。正式系统需从持久化任务恢复，刷新、断网、重启不丢失任务。

### 5.3 监控交易记录

[打开监控交易记录](../../prototypes/交易监控/2026-11-19_监控交易记录_管理端.html)

此页面覆盖所有纳入监控的交易，包括未产生案件者。

- 统计条：纳入监控、已上送、待上送、上送失败；待上送统计包含正在上送的任务。
- 筛选：客户 UID／平台交易号、业务、交易事件、CA 上送状态、成功日期；支持重置、分页。
- 列表：成功时间、平台交易号、客户 UID、业务／事件、原始金额与币种、业务状态、CA 上送状态、关联 Case、详情／补送。
- 交易详情：保留原币与折算字段、网络、CA 受理编号、补送记录；无网络概念的银行／卡交易展示“不适用”。CA 未受理或未返回编号时不得生成伪编号。
- 上送状态：待上送 → 上送中 → 已上送／上送失败。已上送仅指 CA 受理结果已确认。
- 失败补送前，按原交易标识核查受理结果。已受理：仅修正状态；确认未受理：沿用原标识补送；结果未知：保持失败并记录核查，禁止盲目新增一笔上送。
- 同一任务执行中禁止再次补送。最终幂等键、查询接口与重试策略需与 CA 确认；不得把原型的结果选择框放入正式操作流程。

## 6. 字段与数据要求

以下是业务数据要求，不声称对应现有接口字段。具体 API 字段路径、类型、必填、长度和枚举以确认后的 CA 契约及平台接口映射表为准；不虚构接口级约束。

| 数据项 | 要求 |
| --- | --- |
| 平台交易标识 | 稳定关联原业务交易，重试不可产生新的业务交易 |
| 客户归属与业务类型 | 可追溯客户 UID 和上游 customer_identifier；映射至正确类型并保留来源 |
| 业务事件与方向 | 链上入／出、VA 入／出、Card 充值／转出分别保留；方向映射须按业务定义确认 |
| 成功时间 | 记录真实业务成功节点、时区，不能使用重试时间替代成功时间 |
| 原始金额和币种 | 保留原值与精度；展示格式不得改变上送数值 |
| 折算金额和币种 | 与 base_value 对应的来源、汇率和时间需可追溯；缺失不得当零 |
| CA 受理标识 | 原样保存真实返回，辅助核查与去重 |
| 案件／命中标识 | 保留上游原始标识与本地标识关系，不能只凭规则编号区分实例 |
| 统计窗口与命中值 | 保存命中当时的快照，不用当前重新计算值覆盖历史依据 |
| 处理记录 | 案件、操作者、操作时间、前后状态、调查说明、结论与同步结果可追溯 |

业务数据不完整、类型映射未知或币种折算未确定时，应暴露异常以便处理；不能静默填默认零或发送到错误类型以求成功。

## 7. 权限、异常与审计

- 查看权限与处理权限分开；所有查询、领取、草稿、提交和补送必须后端授权，前端隐藏按钮不能代替校验。
- 负责人校验及提交需支持并发冲突处理；重复请求不得重复结案、重复新增结论或重复计数。
- 审计至少记录案件领取、草稿保存、结论提交、同步尝试／结果、受理核查／补送及操作者。敏感凭据、完整鉴权头不进入界面或日志。
- 案件不存在／无权访问按系统规范提示；上游失败、网络错误、空数据分别处理。
- 业务成功与监控故障解耦；监控失败不得回写原交易为失败，也不自动冲正资金。
- 生产告警、重试间隔、最大重试次数、记录保留期限与服务目标待确认，不用演示延迟代替 SLA。

## 8. 验收标准

| 编号 | 验收场景 | 预期 |
| --- | --- | --- |
| A1 | Crypto 失败或处理中交易、USD／Bridge VA、Card 消费进入事件源 | 不被本期成功交易监控误纳入 |
| A2 | 同一客户同时有 Bank 与 Crypto 入金 | 各 type 独立统计，不跨业务拼成笔数／金额告警 |
| A3 | 存在不同原币交易 | 原币分别展示；没有确认的折算依据不直接合计 |
| A4 | 按业务、状态、客户和日期查案件／交易 | 查询和分页正确，无结果明确展示；日期区间错误提示修正 |
| A5 | 两个管理员并发领取 | 只有一个成功；另一方得到冲突反馈，归属不覆盖 |
| A6 | 负责人保存调查草稿后重新进入 | 草稿仍在；非负责人不能修改 |
| A7 | 缺调查说明或未选结论提交 | 阻止提交；完整提交只产生一份处理记录 |
| A8 | 本地结案成功但 CA 同步失败 | 本地结论保留，失败可重试，不重复记录，不影响交易状态 |
| A9 | 上送超时，CA 实际已受理 | 核查后修正状态，不重复上送或重复统计 |
| A10 | 确认 CA 未受理后补送 | 原标识复用，交易记录总数不增加；未知结果不盲补 |
| A11 | Card 转 Wallet | 不重复产生链上入金；时间线保留原始币种，不伪造资金配对 |
| A12 | 结案／升级合规 | 不出现放行／拒绝／冻结资金动作 |

原型已覆盖列表、详情、时间线、领取、草稿、提交、同步失败重试及补送的浏览器演示。A1–A3、A5 等生产接入／并发标准需在真实服务联调验收，不能凭本地演示宣称通过。
