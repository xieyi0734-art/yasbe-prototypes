## 0. 口径声明 —— 「读到的」与「设计的」与「待确认的」

**读到的（仓库内已有，直接引用，不重造）**

- **端别**：平台侧 = 管理端「白标租户管理」；租户侧 = 白标运营后台；开发者文档 = 白标门户。本系统新增端别取值 **`租户业务台`**。
- **角色码体系**：`TENANT_ADMIN`（租户管理员）/ `TENANT_OPERATOR`（租户运营，受限子角色）已在《白标租户管理后台-PRD结构大纲》§1.4 定义。
- **API Key 规范**：环境靠**密钥前缀**区分 —— `sk_test_` / `sk_live_`（不靠请求头）；**密钥只创建时完整展示一次**，列表掩码形态 `sk_test_9f2c••••••••4b71`；平台**只存哈希不存明文**；带 scope、来源 IP 白名单、吊销状态；吊销即时生效；**双密钥并存**支持灰度轮换。
- **Webhook 规范**：POST JSON 到 HTTPS 端点，请求头 `X-YASBe-Signature` + `X-YASBe-Event-Id`；成功判定 HTTP 2xx；**指数退避、最多 8 次、最长 24 小时**，之后进「待重投」可手动重投；单次投递**超时 10 秒**；可能重复投递，用 `event.id` 做幂等去重；签名头 `t=<时间戳>,v1=<签名>`，签名 = HMAC-SHA256(`t + "." + 原始请求体`, 端点密钥)；门户可查每次投递的**状态码 / 耗时 / 响应体片段**。
- **上游真值（Bridge，终端用户与 VA）**：
  - 客户状态枚举 `CustomerStatus` = `active` / `awaiting_questionnaire` / `awaiting_ubo` / `deposits_restricted` / `incomplete` / `not_started` / `offboarded` / `paused` / `rejected` / `under_review`。
  - 认证附加要求结构 `requirements` = `{ complete[], pending[], missing{}, issues[] }`（`issues` 可为字符串如 `endorsement_not_available_in_customers_region`，或对象如 `{ id_front_photo: "id_expired" }`）；另有 `future_requirements[]`（带 `effective_date`）。驳回原因 `rejection_reasons[]` = `{ developer_reason（不对客户展示）, reason（对客户展示） }`。
  - VA 激活状态 `VirtualAccountActivationStatus` = `activated` / `deactivated`。
  - VA 收款信息字段按币种不同：**USD** = `bank_beneficiary_name` / `bank_account_number` / `bank_routing_number` / `bank_name` / `bank_address` / `bank_beneficiary_address`；**EUR** = `account_holder_name` / `iban` / `bic`；**GBP** = `account_holder_name` / `sort_code`（6 位，无连字符）/ `account_number`。
- **业务口径**：「一终端用户 × 一币种 = 一个 VA」；VA **开立即绑定通道**（故多通道冗余只在出金侧成立）；入金归因靠「VA 账号 → 附言 / reference → 上游流水号」三路交叉，产出 `attribution_key`；匹配不唯一 → **挂账待认领**；幂等键 =（`tenant_id` + 端点 + 幂等键）；**一切拦截都在记账之前**；金额一律 string 表达（前端不做浮点运算）。

**设计的（本稿新增，占位待确认）**

- 导航树与 RBAC 三档角色（含角色码扩展）、三个核心页面的线框与字段、开发者中心的两处防呆交互。
- 我方归一后的**终端用户状态机**与 **VA 状态**（上游方言不得直接进 UI）。

**待确认的**：见 §4（9 条，均给推荐口径与影响面）。

### 0.3 全局壳的三个横向常量（每个页面共享）

- **环境切换**：`沙盒 / 生产`（沙盒为一期「受限联调环境」，见 Q8）。**环境状态必须在页头常驻**，并进入深色 / 浅色或角标区分，防止在生产环境做联调、在沙盒里以为发了真实资金。
- **租户上下文**：所有查询强制带 `tenant_id`（行级隔离）；本台**永久只见本租户**，不存在「透视模式」。
- **币种范围**：仅 `USD` / `EUR` / `GBP`（枚举固定三项，不做动态币种列表）。

### 1.3 三级权限守卫（实现口径，与既有隔离规范一致）

1. **路由级**：角色无权的菜单**不渲染**（不是置灰后仍可点）；直接改 URL 进入 → `403` + 审计，**不得静默返回空集**。
2. **按钮级**：只读角色看到的是**禁用态 + 悬浮说明**（「你的角色为 Finance，仅可查看」），危险动作（吊销 Live Key、认领挂账、充值确认）一律二次确认。
3. **数据级**：所有查询强制 `tenant_id` 过滤；角色域再收窄（Finance 只见资金域与流水域，Developer 只见开发者域）。

### 1.4 为什么这样分组（设计说明）

- **按「操作对象」而非「系统模块」分组**：业务 / 资金 / 开发者 三个分组分别对应「看人」「看钱」「看接口」，符合财务与研发各自的肌肉记忆；**不把开发者配置塞进「设置」**——独立门户出身的人会去左边找 API Key，不会去设置里翻。
- **「储备金与账单」是资金分组的首项**（不是末项）：外扣模式下它是**最可能出事的页面**（余额不足即拦单），必须第一眼可见。
- **合并的门户 8 页只保留 4 项进菜单**：服务能力总览 / 快速开始 / API 参考 / 错误码与限流属**文档内容**，落在「API Key 管理」页内的帮助链接与站点文档，不占左侧导航（导航只放**可操作**项）。
- **一页一职责**：沿用本仓管理端约定，不做大 Tab 页；页面之间靠面包屑与抽屉下钻，不靠 Tab 切换。

## 交付物 2 · 核心页面线框与字段定义

> 通用口径注记（三页共用）：
> ① **金额一律 string 存储**（无 number 类型），前端**只做显示格式化**（无千分位运算、不参与浮点计算），显示精度按币种小数位（USD / EUR / GBP 均 2 位）；
> ② **状态值一律用英文归一枚举**，UI 可配中文标签，但**不得把上游方言字符串（如 `awaiting_ubo`）直接打到界面上**；
> ③ **平台专属字段不出现在任何租户可见页面**：风控阈值、上游成本与底价、平台资金归集 / 托管地址、其他租户任何数据。

**余额不足的告警视觉逻辑（三档，必须显式且不可静默）**

| 档位 | 触发条件（推荐口径） | 视觉 | 系统行为 |
|---|---|---|---|
| **充足 SUFFICIENT** | 可用余额 ≥ 预警线 | 卡片中性描边，状态点 `#4ade80` 绿色 | 无横幅；正常放行 |
| **预警 LOW** | 预警线 > 可用余额 > 单笔最高预估手续费 | 卡片琥珀描边 + 顶部琥珀横幅「USD 储备金低于预警线，建议充值」 + 「待办与告警」落一条 | **放行**；通知财务与 Admin（站内 + 邮件） |
| **不足 DEPLETED** | 可用余额 ≤ 单笔最高预估手续费（含 0） | 卡片红描边 + 顶部红色横幅（不可关闭）+ 导航「资金」分组挂红点 | **出金拦截**（拦截在记账之前，拒单不产生账务痕迹）；入金按 Q2 处置；**仍可充值** |

> 视觉纪律：颜色**不单独承载信息**（色盲可用），每档同时带文字标签与图标；「不足」状态在**任何页面**都要有可见入口（导航红点 + 横幅），不允许只在储备金页出现。

**字段表 —— A. 币种余额卡（每币种一张，共 3 张）**

| 字段 | 英文 / 键 | 类型 · 约束 | 来源 / 口径 |
|---|---|---|---|
| 币种 | `currency` | `enum [USD, EUR, GBP]` 固定 3 项 | 本台硬约束 |

**关键交互与口径**

- 三张币种卡**不做汇率折算合并**；缺币种（如未开通 GBP）显示「未开通 · 去开通」而非 `0.00`，避免误读为余额为零。
- 扣费明细**只读**，不允许人工改数；错账唯一纠错手段是**反向冲正**（新增反向分录）。
- 「充值储备金」是唯一写入口：选币种 → 显示平台收款账户与**唯一参考号**（参考号 = 租户维度唯一，用于到账自动认领）→ 上传付款凭证 → 提交。**到账以平台收款账户实际入账为准**，提交不等于到账，页面须显示「待到账 → 已到账」两态。
- ⚠️ **口径边界**：储备金收款账户是**给租户自己的充值通道**，必须展示；这与「平台资金归集 / 托管钱包地址**不向租户展示**」的红线**不冲突**——后者指终端用户资金沉淀点（平台账本科目）。**不得把两者混为一谈做在同一处**。

| 手续费 | `fee_amount` | `string` | **由商户（租户）承担，从储备金扣减**；**不从 `amount` 中扣除** |
| 费用承担方 | `fee_payer` | `enum [TENANT_RESERVE]` | 固定文案「商户承担」 |
| 终端用户实付 / 实收 | `net_to_user` | `string` | **= `amount`**（外扣的定义性结果）；UI 必须显式并列，让财务一眼确认「用户没被扣费」 |
| 储备金扣减后余额 | `balance_after` | `string` | 与储备金页逐笔可对 |
| 计费依据 | `price_snapshot_id` / `fee_model` / `fee_rate` | `string` / `enum` / `string` | 改价不追溯 |
| 费用状态 | `fee_status` | `enum [PENDING_DEDUCTION, DEDUCTED, FAILED, REVERSED, WRITTEN_OFF]` | 储备金不足时转 `WRITTEN_OFF`（欠费挂账）+ 横幅告警 |

> 外扣模式 UI 纪律：**「用户本金」与「手续费」必须在视觉上分成两行、两个量纲标签**，禁止合并成「合计」一行数字——否则财务会误判为内扣。抽屉顶部再放一句固定说明：「本笔手续费由商户承担，终端用户不受影响」。
> 出金时若储备金不足：抽屉显示红色告警条「储备金不足，本笔已拦截（未产生扣费）」+ 状态 `FAILED` / 原因 `RESERVE_INSUFFICIENT`。

## 交付物 3 · 开发者中心 UI 交互防呆设计

### 3.1 生成 API Key —— 密钥安全（分步）

**核心原则：明文只存在一次，且只存在于屏幕上。**

1. **入口分离与权限前置**：`API Key 管理` 是**独立一级菜单**（不藏在「设置」里）。页面顶部固定一句常驻说明：「密钥只在创建时完整显示一次，请立即保存。吊销即时生效。」生成 / 吊销按环境分权——**Live 环境的生成与吊销强制 2FA 二次验证**（Sandbox 可免）。
2. **生成前必须填「名称 + 环境 + scope」**：生成按钮**默认不可点**，直到填写密钥名称（如「生产-收款服务」）并显式勾选环境（`Sandbox` / `Live`，Live 项带红字警示）。目的：阻断「手一滑就在生产生成一把好用的全权限钥」。**scope 默认取最小集**（只勾读权限），写权限需主动勾选并显示影响面（「本 key 将可发起真实出金」）。
3. **「只展示一次」的全屏 Modal**：创建成功后弹出 Modal 展示**完整密钥**（形如 `sk_live_9f2c1a8e…4b71`），并提供：一键复制（**焦点默认落在复制按钮**，不是关闭按钮）、`sk_live_` 前缀说明、环境的接入域名。**关闭按钮初始为禁用**，须勾选「我已妥善保存，关闭后无法再次查看」才可点——防止肌肉记忆式回车关掉。
4. **关闭即不可逆**：Modal 关闭后**任何位置都不再提供「查看」入口**；服务端**只存哈希**（不存明文，平台侧管理员也看不到）。若要找回，只能吊销后重建——UI 上把这条写成明文提示，而不是让用户找客服。
5. **列表掩码展示**：列表永远显示 **前 4 位 + 8~10 个 `•` + 后 4 位**（沿用既有门户形态 `sk_test_9f2c••••••••4b71`），**不提供「眼睛」图标**。列上同时给出：环境徽标（Sandbox / Live 双色）、scope 摘要、来源 IP 白名单（有 / 无）、**最后使用时间**、创建人、状态。
6. **轮换防呆（避免「换钥即断服」）**：支持**双密钥并存**——先新建一把新钥、把服务切过去、观察「最后使用时间」确认旧钥无流量、再吊销旧钥。UI 在吊销弹窗里**显示该 key 的最后使用时间与近 24h 调用量**，并在最后调用时间 < 5 分钟时给红字警告（「该 key 近 5 分钟仍在被调用，吊销会立即中断线上服务」）。
7. **吊销 / 危险动作二次确认**：吊销需二次确认，且**要求输入该 key 名称的末 4 位**（不是「确定 / 取消」两个按钮就放行）——成本低但足以打断误操作。吊销后状态置「已吊销」并**保留在列表里**（不删除，留痕），可看到吊销人与时间。
8. **不可复制的细节防呆**：密钥**不进 URL、不进日志、不进审计详情**（审计只记 key 名称与 ID）；页面对密钥字段做 `autocomplete="off"` 与禁止浏览器保存；复制成功后按钮变「已复制 ✓」2 秒后复位，避免用户重复点导致以为没复制。

### 3.2 Webhook 投递失败 —— 日志展示与自助排障

**核心原则：让租户在**不联系我们**的情况下自己定位到「是我端点的问题还是配置的问题」。**

1. **端点级健康度常驻**：`Webhook 端点` 列表每行显示：端点 URL（掩码路径）、订阅事件数、**近 24h 成功率**、最近投递时间、最近失败时间、**熔断状态**（正常 / 连续失败已自动暂停投递）、端点密钥（掩码 + 重置入口）。
2. **失败日志表（投递日志页）**：

| 列 | 键 | 说明 |
|---|---|---|
| 事件 ID | `event_id` | 幂等去重键（也是重投的依据） |
| 事件类型 | `event_type` | 如 `fiat.deposit.settled` / `payout.returned` |
| 投递时间 | `delivered_at` | 每次尝试一行 |
| HTTP 状态码 | `response_status` | `2xx` 绿 / `4xx` 黄（多为配置错） / `5xx` 红（你的服务异常） / `timeout` 红 |
| 耗时 | `duration_ms` | 接近 10s 的给黄色（即将超时） |
| 尝试次数 | `attempt_no` / `attempt_max` | 如 `3 / 8` |
| 下次重试时间 | `next_retry_at` | 指数退避；无剩余次数时显示「已进入待重投」 |
| 响应体片段 | `response_excerpt` | 前 200 字符，可展开看完整（便于发现「回了个 HTML 错误页」） |
| 操作 | — | 重投 / 复制原始 body 与 headers / 查看详情 |

3. **三态清晰不可混**：`重试中`（自动，带倒计时）→ `待重投`（自动已耗尽 8 次 / 24h，只能人工）→ `投递成功`。**「失败」不等于「放弃」**，UI 必须区分「还会自己重试」与「需要你点一下」。

4. **自助排障入口（按「从易到难」排布在同一页，不做成四个孤立页面）**：
   - **① 错误诊断行内提示**：每条失败记录旁直接给「可能原因 + 下一步」，例如 `401` → 「签名校验失败：确认使用**原始请求体**校验，不要用反序列化后再序列化的内容」；`404` → 「端点 URL 不正确或已被关闭」；`5xx` → 「你的服务返回了错误，请查服务端日志」；`timeout` → 「单次投递超时 10 秒，请**先落库立即返回 2xx**，再异步处理」。
   - **② 复制现场**：一键复制**原始请求体 + 请求头**（`X-YASBe-Signature` / `X-YASBe-Event-Id`）与等价 `curl` 命令，让租户在本地即可复现并调试验签，不必等我们再投一次。
   - **③ 发送测试事件**：端点详情里提供「发送测试投递」按钮（Sandbox 与 Live **分开**，Live 带红色提示），立即投一条样例事件，验证 URL 可达 + 验签是否正确，**结果当场回显状态码与耗时**。
   - **④ 手动重投**：单条「重投」+ 批量「重投全部待重投」；重投**带同一个 `event.id`**，并在 UI 上提示「你的端点应按 `event.id` 幂等去重」。沙盒环境另有 `POST /v1/sandbox/webhook-events/{id}/redeliver` 供自动化测试。
   - **⑤ 签名自检**：展示本次投递的 `t=` / `v1=` 头值，并给出可复制的验签示例代码（HMAC-SHA256(`t + "." + 原始请求体`, 端点密钥)）；**不在页面上要求输入端点密钥**——需要重置端点密钥时走「重置」并明确提示「旧签名立即失效」，若要灰度轮换则提示「可同时保留两个密钥一段时间」。

5. **配置环节的防呆（把故障挡在配置时）**：
   - **端点 URL 只接受 HTTPS**；保存 / 启用前**必须通过「验证投递」**（系统发一条 challenge 事件，端点须回 2xx），未通过不允许保存为启用态——杜绝「存了一个永远 404 的地址」。
   - **禁止内网 / 回环 / 私有地址**（`127.0.0.1`、`10.x`、`192.168.x`、`169.254.x`、`localhost`）——既是 SSRF 防护，也直接给出「你的本地开发地址无法接收线上投递，请用公网可达地址或沙盒」的说明。
   - **订阅事件必须显式勾选**，默认**不订阅任何事件**（避免「全订阅」导致端点被淹没）；每个事件旁给出触发条件与建议处理动作（沿用门户「事件与通知」页已有的事件表）。
   - **熔断必须显式告知**：连续失败达阈值后自动暂停投递，同时弹站内 + 邮件告警，并在端点行显示「已暂停投递 · 恢复」；**恢复需人工点确认**并再走一次验证投递——不静默恢复（否则会在无声中又失败）。
   - **页脚常驻一句真实提醒**：Webhook 是**通知**不是**真值源**——「不要只依赖 Webhook，请用对账接口兜底」，正文里给对账 / 补拉接口的跳转。这条能省掉大量「为什么我没收到回调」的工单。
