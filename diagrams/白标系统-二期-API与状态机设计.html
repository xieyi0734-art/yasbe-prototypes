谁在推状态（三个来源）

① 租户系统（API）：建档、提交、补件、复议。② 我方运营（人工）：审核通过 / 驳回 / 补件结论、冻结 / 解冻。③ 上游通道：上游侧另有独立审核与风控，其结果由适配层归一化后并入本状态机；两边不一致时以更严者为准（例：上游冻结 → 我方同步 Frozen）。

状态 → 可用能力（研发边界）

仅 Approved 可开立子账户（VA / 加密地址 / 卡）。Init / PendingReview / ActionRequired 只能读与改资料，开子账户一律 409 user_state_conflict。Frozen 禁止新开子账户与出金，已有子账户只读（入金可入但入账后即冻结）。Rejected 除复议外全部拒绝。

与一期口径的对应

一期定稿：只做 KYB 不做个人 KYC；法币 / 加密 / 卡片按模块各自独立审核，任一模块未过不影响其它模块。因此本状态机按 user × module 维度实例化：一个终端用户可同时是「法币 Approved + 卡片 PendingReview」，页面与 API 返回都按模块给状态（= 一期「部分生产」在客户维度的延伸）。

鉴权与密钥

请求头 Authorization: Bearer <API Key>，一租户一 key；一期分受限 key（限额度 + 收款人 / 地址白名单，用于联调）与生产 key（过闸门后解除额度限制）；一期无沙盒，联调环境就是生产接口。轮换与吊销在开发者门户操作（写审计日志），旧 key 保留 24h 双活以便平滑切换。

幂等（硬规则）

所有 POST / PATCH 必须带 Idempotency-Key（建议 UUIDv4）。同键 + 同请求体 → 返回首次结果（含同一资源 ID），不重复开户 / 不重复出金；同键 + 不同请求体 → 409 idempotency_key_reuse。资金类接口缺键直接 400 idempotency_key_required（不放行「允许但风险自负」）。

分页 / 金额 / 错误

分页：游标式 cursor + limit（≤ 100）+ has_more，流水倒序。金额：一律最小单位整数（分 / cents）+ ISO 4217 币种，避免浮点；出金响应带 fee 明细（费率取自该租户的定价配置）。错误：{ code, message, request_id, details }，内容协商 JSON；关键码：401 invalid_api_key · 403 module_not_enabled · 409 user_state_conflict · 409 idempotency_key_reuse · 422 validation_failed · 429 rate_limited · 503 upstream_unavailable。

版本与兼容

版本走路径 /v1；不兼容变更升 /v2，兼容性新增（加字段、加事件类型）不升版但要公告。响应一律含 request_id，用于与租户对账排障；Webhook 事件体同样带 event_id + request_id，便于逐笔追平。

四个关键设计点

① 归因靠 VA 号，不靠付款方附言 —— 到账即自动认到终端客户。② 上游 Webhook 是入金的唯一触发源，终端用户 / 租户都无需发起；租户只收我们的 Webhook。③ 记账在归因之后：归因失败 → 挂账不记账（账实一致优先于时效）。④ 重复通知按上游流水号幂等，同一笔钱绝不重复入账。

与一期的对应

一期定稿 §入金异常：金额不符 / 来源不明 → 挂账待处理；上游退回 → 原路退回并通知；重复通知 → 幂等。异常三条在本图全部落到分支上，不是文字承诺。价格快照与复式记账对应公共尾部的账本服务（改价不追溯）。

为什么多画一个「通知服务」

业务服务不直接调租户回调地址：事件先进通知服务统一投递（签名、退避重试、最终失败告警、投递记录可查），这对应一期「三处可见」与「Webhook 投递失败 → 重试 → 最终失败告警」的定稿口径。租户若只认「我们系统」也可把它理解为网关的异步出口。

PM 备注 投递规则（沿用一期定稿）：事件先进通知服务 → 按订阅过滤 → HMAC 签名投递 → 指数退避重试 → 最终失败告警；租户可查投递记录并自助补偿查询（对应 API /v1/webhook-deliveries）。至少一次投递语义：租户必须按 event_id 去重（我们可能重投同一事件）。
