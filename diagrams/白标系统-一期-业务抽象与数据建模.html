③ 分层说明每层是什么 · 换了会怎样 · 本期边界在哪

L0 · 参与方 ACTOR

租户系统（唯一集成方，持 API Key）、终端用户（无我方入口，只经租户界面）、我方运营。三者都不直接触达上游：这是白标的定义性边界 —— 终端用户甚至不知道平台存在。

L0 · 界面层 UI

三个完全独立的前端工程：白标门户（外部开发者自助）、租户业务台（租户内部用）、平台运营总台（我方内部用）。三者不共享代码，可独立发版 —— 这是前端工程量的切分依据。

L1 · 接入层 GATEWAY

统一入口：API Key 鉴权与签名、限流、幂等键、版本。核心动作是租户上下文注入 —— tenant_id 一经解析就贯穿全链路，下游所有查询与写入都必须带它，这是多租户隔离的唯一实现点。上游 Webhook 走独立入口，不走此层。

L2 · 平台服务层 SERVICE

法币能力的领域实现。四个核心服务：法币服务（开户 / 归因 / 收付）、路由引擎（决定走哪家）、账本服务（钱的真值）、计费服务（按租户定价收钱）。法币服务不直接调上游，一律经 L3。加密服务与发卡服务标【二期 Phase 2】，本期不建。

L3 · 通道适配层（防腐层）

本层就是 Anti-Corruption Layer，拆两件东西：防腐归一内核（状态字典 / 字段映射 / 错误码归一 / 原始报文落库，全通道共用）与每上游一个适配器（协议、凭据、验签各自封装）。换上游只动 L3，L2 一行不改；上游方言永不渗进 L2 代码。

L4 · 上游提供商层

一期 2 家：Bridge 覆盖 USD · EUR · GBP 三币种，OpenPayd 覆盖 EUR · GBP 两币种。因此 USD 只有一条腿（Bridge，无冗余），EUR 与 GBP 有两条腿（Bridge 与 OpenPayd，Multi-Rail）。加密托管与发卡上游为二期虚线，不计入本期交付。

④ 交付物 3 · 核心名词解释表（Data Dictionary）给产研团队对齐口径用 · 末列是易错点，评审时逐条过

名词（英文 / 缩写）一句话定义在本次 BaaS MVP 业务中的具体含义关键设计约束与易错点
虚拟账户
Virtual Account (VA)		 由上游持牌机构在指定通道上开立的、以终端用户名义收款的收款账号，不是平台自己开的内部记账账户。 落点在 FIAT_ACCOUNT。形态是 IBAN / 账号 + 路由码（Sort Code 等）。它是入金的物理落点，也是资金归因的唯一锚点。开立规则：一终端用户 × 一币种 = 一个 VA。 VA 在开立那一刻就绑定了通道（Bridge 开的 VA 只能收 Bridge 通道的钱）。所以：多通道冗余只对出金有意义，入金侧一旦开户就锁死通道。若要求同一用户同币种可双通道入金，就得开 2 个 VA 并把两组收款信息都给客户看 —— 体验与对账成本都上升。这是 MVP 必须拍板的第一取舍。
全局账本
Global Ledger		 平台内唯一、只可追加的复式记账账本：记录谁的钱、在哪、多少，是所有余额、账单与对账的真值源。 落点在 TRANSACTION_LEDGER。一期把「业务流水」与「账本分录」合在一条记录视图里（字段以【流水】【账本】前缀分组）。全租户共用一张账本，但每条记录强制带 tenant_id，按租户强隔离。 三条铁律：只新增、不修改、不删除（错账用反向冲正 reversal_of）；状态与余额解耦（通道回调是证据，不能直接改余额，余额只能由分录推导）；一切拦截都在记账之前（拦截等于零账务痕迹，钱一旦在途失败只能冲正）。易错点：把上游回调当记账指令直接改余额。
多通道路由
Multi-Rail Routing		 同一币种存在两条及以上上游通道时，按规则决定「这一笔走哪家」的机制。 落点在 ROUTING_RULE + L2 路由引擎。本业务：USD 单通道（Bridge，不可路由）；EUR / GBP 双通道（Bridge 与 OpenPayd，可路由，可取主备或加权分流）。 判定链顺序不能变：幂等命中 → 准入 → 风控拦截 → 额度 → 头寸 → 选路 → 通道健康度 → cut-off → 调用，命中即停。每笔必须落 hit_rule_id，否则事后解释不了「为什么走这家」。最易做错的一条：超时或 5xx 的第一动作是查单，不是重试（上游可能已受理只是响应丢了，盲重试等于重复出金）。
防腐层
Anti-Corruption Layer (ACL)		 隔离上游「方言」的翻译层：上游的字段名、状态枚举、错误码、金额单位，一律不得渗进我方领域模型。 本层 = L3，拆两件：防腐归一内核（字段映射 / 状态字典 / 错误码归一 / raw_payload 原样落库，全通道共用）+ 每上游一个适配器（协议、凭据、验签）。核心价值：换上游只动 L3，上层零改动。 归一必须有字典且字典必须闭合：Bridge 的 COMPLETED 与 OpenPayd 的 EXECUTED 都归一为 SETTLED；字典外的状态一律判 UNKNOWN，不推进、不记账、挂人工（上游偷改枚举是常态，不认识就不猜）。易错点：为省事在上层直接判断上游原始状态字符串。
资金归因
Attribution		 把一笔进入平台的资金，自动判定到「哪个租户的哪个终端用户、对应哪个 VA、用于哪笔业务」的过程。 出金归因容易（我们主动发起，自带外部引用号）。入金归因是本模块最难的一环：钱是别人打进来的，需三路匹配 —— VA 账号（打到哪个号）→ 附言 / reference（客户主动填写）→ 上游 Webhook 的流水号。三路交叉得出 attribution_key，它同时是对账主键。 只有三种合法出路：唯一命中 → 记账并回调租户；多义命中 → 挂账待认领；无匹配 → 挂账。绝不允许默认归到某个客户账上，也绝不允许直接退款了事。易错点：只用金额匹配（同额同日多笔必然撞车）。挂账必须有独立看板与时效告警，否则钱会静默躺在系统里。

⑤ 配套术语速查上面五个是核心概念，这些是评审时高频出现的配套词汇

术语全称 / 英文本次业务口径
租户 / 白标租户Tenant下游 B 端企业。它有自己的客户与自己的品牌界面；我们的名字不出现在终端用户面前。数据隔离的根实体。
API KeyAPI Key发给租户的访问凭据。平台只存哈希不存明文；带环境（sandbox / production）、权限范围（scope）、来源 IP 白名单与吊销状态。
多租户隔离Tenant Isolation不是「加了 tenant_id 就算隔离」：鉴权、查询、写入、回调、计费、日志六个环节都要带 tenant_id，且数据库层要有兜底约束。
身份与资产解耦Identity-Asset DecouplingUSER_PROFILE 只管合规身份，FIAT_ACCOUNT 只管资产。换通道、加币种、冻结账户都不动身份主档；反之身份信息变更也不必重建账户。
幂等键Idempotency Key租户发起资金类请求必须带。构成 =（tenant_id + 端点 + 幂等键）。重试与重放都靠它兜住，避免重复开户、重复出金。
上游流水号upstream_ref / Ext_ref上游通道给这笔业务的编号。对账双向匹配与争议举证的主键，必须与 raw_payload 一并落库且不可修改。
原始报文raw_payload上游 Webhook 的原样报文归档（含验签结果与时间戳）。对账核不平时的第一手证据，不允许只存归一后字段。
反向冲正Reversal已记账业务出错时的唯一纠错手段：新增一笔方向相反的分录指向原交易，原记录保留。禁止 UPDATE / DELETE 流水。
平台账户 / 主账户Master Account我方在每个上游通道持有的资金池。出金实际从这里出，故需余额监控与调拨；终端用户看不到它，它是平台账本内的科目而非客户资产。
截单时间Cut-off Time上游通道当日处理截止时刻。过点提交即为次一工作日，路由与到账时效承诺必须考虑它。
KYBKnow Your Business对租户（企业主体）的合规审核，区别于对终端用户的合规身份审核。二者不可互相替代。
资金归集 / 归因落点Sweep / Landing Point资金最终沉淀到我方主账户的链路；归因落点指入金在哪一层被判定归属（本设计定在 VA + 附言 + upstream_ref 的交叉匹配）。
