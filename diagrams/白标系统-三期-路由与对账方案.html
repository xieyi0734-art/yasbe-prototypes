① 重试边界（最容易出错的地方）

只对可安全重试的失败重试：连接超时、5xx、限流。但 5xx / 超时的第一动作永远是「查单」，不是重试 —— 上游可能已受理只是响应丢了，盲目重试 = 重复出金。重试必须带同一 Idempotency-Key，退避 1s / 2s / 4s + 随机抖动，最多 3 次；查单确认「未受理」才真正重发。

② 熔断与降级

触发条件：近 5 分钟失败率 ≥ 50% 且样本 ≥ 10 笔（避免一两笔抖动就熔断）。熔断时长指数递增 60s → 2min → 5min，之后半开：只放 1 笔探活，成功即闭合、失败再熔断。降级顺序：同币种备用通道 → 排队等恢复；两者都不可用才给 503 channel_circuit_open，且是排队不是拒单（业务连续性优先，钱一分没动）。

③ Master Account 余额三道防线

事前：每个通道设「最低保留余额」，低于阈值提前告警并触发调拨 / 入金（不等出金时才炸）。事中：出金前校验「可用余额 ≥ 本笔金额 + 费用」，不足则拒单 + 不扣账（宁可拒单不给单边账），有备用通道则自动切换。事后：T+1 对账核对通道头寸，差异回到第 3 节处理。

④ 为什么拦截必须前置

风控 / 额度 / 余额 / 通道健康四类拦截全部在记账之前：拦截 = 零账务痕迹。钱一旦扣出（在途），后续失败就只能走反向冲正（回冲分录），而不是删记录 —— 账本只追加、不修改，这是对账能核平的前提。

防腐层的三条硬规矩

① 原始报文只进不出：上游报文原样落库（含验签结果），任何时候可回溯「上游当时到底说了什么」。② 业务层只见内部模型：字段名、状态枚举、错误码、金额单位全部在适配层抹平，业务代码里不允许出现 COMPLETED / EXECUTED。③ 未知即停：上游偷偷加枚举是常态，遇到不认识的状态就 UNKNOWN 挂人工，绝不「猜一个最像的」。

为什么要留 raw_payload

对账和争议最终都要回到上游原始报文：金额单位（分 / 元）、币种写法、费率表达、时间与时区，各家不同。保留原始报文 + 归一化结果成对留档，才能证明「我方记账没错，是上游改了字段」。这也是第 3 节差错处置的举证材料。

  • 导入幂等：每个外部文件按「通道 + 业务日 + 文件指纹」去重，重复导入不产生二次核对。
  • 原始归档：所有原始文件与报文按合规年限归档，核对结果可复现（重放同一份文件应得到同一结论）。
  • 时区口径：统一按通道所在地业务日 + 我方 GMT+8 双时间戳记录，避免「跨日 = 差错」的误判。

3.2 对账核心逻辑（三层双向核对）

  • L1 · 头寸核对（总量）：上游期末余额 vs 我方账本该通道「在途 + 托管」余额，按通道 × 币种核对；不平则下钻到 L2 定位具体流水。加密无「账户余额」概念 → 改为「地址余额 + 未确认提现」核对。
  • L2 · 明细双向核对（双边匹配）：双向都查 —— 我方有、上游无 = 我方单边账；上游有、我方无 = 上游单边账。匹配键优先级：upstream_ref → (金额 + 币种 + 日期 + 收款人 / 地址) → 模糊匹配后进人工。匹配窗口取 T-1 / T / T+1，吸收 cut-off 与到账时差。
  • L3 · 状态一致性核对：同一条流水，我方终态（SETTLED / FAILED / RETURNED）与上游终态逐笔比对；不一致 → 反向冲正 + 更正 Webhook（这是「账平了但业务错了」的唯一防线）。
  • 差异分级：① 金额差（手续费 / 汇率 / 小费，容差内自动调账）② 状态差（自动冲正）③ 记录差（单边账，人工判定归属）④ 时点差（跨日，规则白名单，不算差错）。
  • 输出：对账报告 + 差异清单 + 自动处置日志；对租户侧产出结算单与对账文件（STATEMENT / RECON_FILE），并推 reconciliation.completed 事件。
  • 分产品差异：法币 = 文件驱动、按业务日核（本方案主体）；加密 = 按 tx_hash 核、须过确认数阈值、考虑手续费与找零、容忍区块重组（reorg）；卡片 = 授权与清算两段式，按 auth_id 关联，跨币种结算含汇率差与小费调整。

处理原则（五条总纲）

① 自动优先：可判定的差异（容差调账 / 去重销账 / 移窗）全自动，人只处理「归属不明」。② 资金先挂住：宁可挂账不动钱，也不猜着入账。③ 账本不可变：一律新增冲正分录，禁止修改历史。④ 分级时限：T+1 发现、T+2~T+3 处置，超时自动升级告警。⑤ 全链留痕：每次处置写审计日志（谁 / 何时 / 改了什么 / 依据哪份文件）。

与一期 / 二期的接口

对账结果落到一期的 RECON_FILE / STATEMENT 实体，差错处置写 AUDIT_LOG；涉及资金动作（回冲 / 补记）产生的交易与分录，沿用二期 API 的幂等与 Webhook 口径通知租户（payout.returned / reconciliation.completed）。

对账不平的兜底顺序

先重放文件（排除导入错）→ 再扩窗匹配（排除时点差）→ 再查原始报文（排除归一化错）→ 最后才判为真差错进差错池。顺序不能倒：90% 的「不平」其实是前两步能消掉的假警报，直接进差错池会把人工淹掉。

Health Check / 熔断通道健康度探活 + 熔断器（闭合 → 打开 → 半开）。不健康的通道不派单，有备用就切、没备用就排队。
Cut-off（时间窗）通道当日受理截止时间。过窗即顺延下一工作日，必须提前告诉租户预计到账日，否则「慢」会被当成「丢」。
Adapter / 防腐层把上游的字段、状态、错误码、金额单位、币种写法抹平为内部统一模型；业务层永远看不到上游方言。
raw_payload上游原始报文存档。争议与对账举证的根，与归一化结果成对留档。
Ext_ref（上游流水号）对账第一匹配键，贯穿「上游报文 ↔ 归一化事件 ↔ 交易 ↔ 账本分录」四层索引。
Clearing File卡组织的清算文件：与授权流水按 auth_id 关联，是卡业务核平的唯一依据（授权≠清算）。
单边账一方有记录、另一方没有。分「我方单边」「上游单边」，处置方向完全相反：前者回冲释放，后者补记待查。
反向冲正 / 回冲用新增一笔相反分录抵销原分录（账本不可变），而不是删除或修改原记录。
挂账资金先搁置不入账、限期处置；超期按规则原路退回或升级人工。对账差错的第一处置动作。
